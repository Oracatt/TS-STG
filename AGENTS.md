# TS-STG engineering rules

- Manage this project with Git. Inspect pre-existing changes before editing, and record completed, validated work in focused local commits. Do not sweep unrelated changes into a commit. Generated build/report output, title-specific demo media and user data remain untracked. The common packs in packages/thlib/assets/reference-common, touhou-common and spell-common are part of thlib and must be versioned with their manifests and notices.

- Boss HP exhaustion is a scriptable stage event, never an implicit inversion/explosion or a mandatory two-choice explosion/escape state machine. Let consumers retain the body for dialogue, resume another phase, remove it silently, compose public exit/effect presets, or run their own sequence. Keep settlement, drops and cancellation separate unless the caller explicitly selects a bundled preset.

- C++ owns platform services only: script runtimes, rendering, resources, audio, input, files and timing. Keep bullet/player/enemy/collision/bomb/spell/score/stage/menu/replay rules in portable TypeScript thlib (compiled to standard JS).
- thlib includes the complete reusable application framework and restored player, weapons, Bombs, bullet/laser animation, effects, ordinary enemies, items, HUD, menus, pause/results and their common assets, not only simplified templates or selected textures. The user's latest correction explicitly requires TH20-source Boss entrance double circles, background distortion, countdown and SpellCardAttack as ready-to-use public presets, alongside Reimu/Marisa bodies, options, shots, hit indicators and complete Bomb animations. Use Touhou20Reconstruction as the original visual baseline; RushBoss's different warp/rings/HUD must not replace this default. Bold refactoring is authorized. A resource originating in TH20 is not automatically TH20-exclusive. Only branding/title-specific artwork, concrete Boss identities/attacks/portraits and specific stage/spell backgrounds belong in the consuming application. Generic UI layout, animation and application composition belong in thlib with injectable skins and stages. Mixed atlases must be filtered where needed, not used as a reason to omit whole features. Shared faithful profiles retain restored numerical defaults. Applications depend on thlib, never the reverse. Preserve original source hashes and provenance, and document transparent masks/script transformations; do not mislabel original artwork as MIT. The public entry is @ts-stg/thlib/touhou, not a game-specific /th20 alias.
- `@ts-stg/thlib` must work without Node, browser globals or the native host. Adapters belong in example/application entry points. Simulation time is fixed integer frames; use seeded RNG for game randomness.
- SpellCardEditor is a TypeScript/JavaScript source editor and native preview tool. Treat authored TS/JS as the sole editable document; compile a temporary preview copy only; never regenerate user code from a visual model. The user explicitly removed the editor's fixed spell-card event interpreter, its public document APIs and legacy JSON conversion. Require a user-authored createSpell(context) runner; keep preview metadata validation, code-editor dependencies, files and transport outside thlib. This removal does not concern the game's independent Boss phase clocks or animation timing.
- The local Touhou20Reconstruction directory is read-only. The user's updated requirement is faithful original behavior and presentation, using TH20 reconstruction as the concrete reference. Original assets may be read/copied into the appropriate common thlib packs or ignored local demo directories for this authorized restoration work; never include original executable code. The user explicitly authorized committing the three common packs to the private GitHub repository on 2026-10-08. Keep their original rights notices and provenance; repository inclusion does not relicense them. Title-specific demo resources remain ignored. Mark unsupported or unverified behavior explicitly; passing generic-engine tests is not evidence of original-game equivalence.
- Implement supported features concretely. Additional JS backends require an implementation and tests before being advertised as available. Windows x64 builds embed V8 and QuickJS-NG; auto selects V8, and explicit --backend quickjs remains available. Both share the same portable JS and host ABI. Backend changes require host boundary tests, gameplay and image equivalence, and serial same-workload GPU profiling.
- Keep public ESM exports, declaration files and examples consistent. Preserve the generic drawing ABI documented in ARCHITECTURE.md.
- Validate gameplay changes with relevant node:test tests. Validate host changes with CMake build/CTest and native fixtures. Run `node tools/verify-integration.mjs` after changes that affect the full simulation or runtime boundary. Verify visual changes using native `--screenshot` and inspect the image.
- Benchmark the actual QuickJS backend before making native performance claims. Node benchmark results alone do not establish native frame rate.
- Do not publish a package, repository or release unless requested. Local build and packaging are normal development actions.
- Release scope is only the native engine and thlib (including common assets and necessary API docs/licenses). examples/danmaku is a development/demo application, not release payload. Default package.ps1 must create this SDK with an explicit allowlist. The native default entry is the consumer project's main.js.
- The user's subsequent clarification is explicit: Rush is content reference, not a source of gameplay mechanisms. Use only its Boss/stage art, spell trajectories, dialogue and BGM. Hitboxes, repeated graze, damage rules, Bomb cancellation, spell bonus/settlement, HP defaults and common presentation come from thlib's original-style owners; never retain Rush cleanOnHit/cleanOnBomb immunity, damage ramps or duplicate bonus clocks. The library must stay suitable for publication, with no Rush-specific branches. Consult the local LuaSTG/THlib reference for uncertain framework ownership decisions, while keeping TH20 as the numerical/presentation baseline. BGM is game-specific: Rush uses its own six tracks, including Player's Score; no game's BGM belongs in thlib or the default SDK. Shared music transport and game-over save/switch/restore lifecycle belong in thlib, with track keys and files injected by the consumer. Boss appearance/entrance readiness is not combat activation. Replays must be versioned whenever these deterministic mechanics change.
