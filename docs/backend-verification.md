# 原生脚本后端对照

`tools/verify-backends.mjs` 在同一个 Release 原生程序中显式选择 `--backend quickjs` 和 `--backend v8`。V8 是嵌入 C++ 宿主的脚本引擎；游戏没有改为 Node 进程，也没有获得 Node 的文件、网络或进程接口。渲染、资源、音频和路径规则仍由相同的原生平台服务提供。

```powershell
# 全部按顺序执行，避免同时测两个运行时。
node tools/verify-backends.mjs --exe build/Release/ts-stg.exe

# 可分别执行，报告写到 reports/backends。
node tools/verify-backends.mjs --scope host
node tools/verify-backends.mjs --scope runtime
node tools/verify-backends.mjs --scope graphics
node tools/verify-backends.mjs --scope performance

# 将四份报告汇总；必须与当前二进制和生产 JS 哈希完全相同。
node tools/verify-backends.mjs --scope aggregate
```

`--out` 可指定另一个报告目录。执行过程中 JS 源文件和二进制的 SHA-256 必须保持不变。比较报告列出二进制哈希、公共库与业务代码哈希、操作系统、CPU、GPU 和各运行的原始 profile。

## 正确性范围

- 宿主检查实际执行循环 ESM、模块缓存身份、活绑定、可完成的顶层 await、已处理的 Promise 拒绝及逐帧微任务。两后端都必须拒绝未完成的顶层 await、异步 update、脚本异常、未处理拒绝、超过 10,000 个微任务、超时的无限循环、无效 draw 命令/渲染状态、失效资源和越界路径。TypedArray 子视图必须遵守 byteOffset/byteLength。单独的 V8 夹具断言 `tsstg.backend === 'v8'`，并检查没有 `process`、`require`、`Buffer`。
- 仿真检查使用 Node 作为独立便携 JS 参考，分别对照两原生后端：29 个阶段 × 4 难度 × 2 自机 × 600 帧，共每后端 139,200 帧。完整 `RushBattle.snapshot()` 的有限 JSON 值严格相等，包含 Boss/自机位置、帧计数、武器/Bomb 状态、得分、RNG 和发射哈希。JSON 仅统一正负零，没有额外取整或容差。
- 仿真的额外实体二进制浮点字段单独报告，不以严格统计快照通过来声称全部实体字段按位相同。不同脚本引擎的 `Math` 库可在原始角度、长度、力等字段产生末位差异；报告保留数量、字段、最大绝对差及示例。
- 每后端还实际执行 420 帧应用录制与 420 帧回放，覆盖中文对白、原作暂停/恢复、自机射击及移动。记录通过原生 userdata 写入，再由新的 `SaveStore` 实例读回后播放；回放期间注入实时 Bomb/移动输入。录制末状态与回放末状态哈希必须一致，两后端最终完整 session 也必须严格相等。
- 图形检查运行当前竖屏应用的 24 个真实 GPU 场景，包括主菜单及切换、中文对话、Boss 入场/开卡/扭曲、灵梦/魔理沙 Bomb、暂停、结算和回放。另有通用 quad、3D mesh、纹理切换及像素读回夹具。PNG 解码后的每个 RGBA 通道必须完全一致。完整图形快照的整数/离散值严格相等；仅原始非整数浮点字段允许 `1e-12 * max(1, |a|, |b|)` 的差，所有差异显式记录。这个容差不会应用到游戏统计验证或图片像素。

这些比较验证后端替换没有改变当前实现的行为与画面。它们没有运行东方原作 EXE，不能据此声称与原作逐像素或全部状态相同。

## 性能范围

性能测量每组按 QuickJS、V8、V8、QuickJS 的 ABBA 顺序运行，同一组每后端两次，不并发。主页面、Sunny 第二阶段和 Artia 最终符卡各运行 1800 帧，前 600 个完整渲染帧为 JIT/资源预热，统计后 1200 帧。Boss 阶段必须仍活跃，固定输入、种子、自机、难度、资源和原时间轴保持一致。各次捕获的状态与 RGBA 也必须通过比较。

另外单独测量 Artia 最终符卡最初 300 帧，前 60 帧不计，覆盖早期曲线激光密集窗口。这组窗口预热较短，不能和 600 帧预热后的长序列混为同一种结果。

原生 profile 分别记录 JS update、JS render、命令解码、CPU 提交、GPU 查询、音频和显示等待。`frameWorkMs` 是实际 CPU 工作成本，排除帧率限制/显示等待。它不是原生程序总耗时除以帧数，也不是纯 GPU 时间。声音/音乐音量置零，但音频资源和调用仍执行；没有减弹、跳帧或删减原作粒子。

运行基准前需结束其它游戏预览和高 CPU/GPU 验证进程。报告表明的是列出的场景/时间窗口，不能自动推广为所有符卡稳定 60 FPS。

## 本机验收结果（2026-10-03）

同一 Windows x64 Release 二进制，SHA-256 `b9c78ba26ea23bd09499f273c411ed33c980b2727721b79c28d25e6bf0b68750`，GPU 为 NVIDIA GeForce RTX 3060 Laptop GPU。所有其它编译、测试及游戏预览退出后执行 ABBA。下表为两次运行的平均 `frameWorkMs`，P95 列为两次运行各自 P95 的最小至最大值，单位均为 ms。

| 场景 | 总帧 / 预热 | QuickJS 平均 | V8 平均 | QuickJS P95 范围 | V8 P95 范围 | 工作耗时比 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 主页面 | 1800 / 600 | 8.47 | 2.54 | 11.52–11.67 | 3.08–3.13 | 3.34× |
| Sunny 第二阶段，Lunatic，灵梦 | 1800 / 600 | 38.02 | 5.21 | 43.18–43.72 | 6.46–6.47 | 7.30× |
| Artia 最终符卡第 601–1800 帧，Lunatic，魔理沙 | 1800 / 600 | 13.07 | 1.89 | 33.31–33.37 | 3.61–3.86 | 6.91× |
| Artia 最终符卡早期曲线激光窗口 | 300 / 60 | 46.53 | 6.00 | 53.01–54.07 | 7.74–8.26 | 7.75× |

早期曲线激光窗口中，JS update 平均由 13.83 降至 1.30 ms，JS render 由 30.83 降至 1.67 ms；主要瓶颈确实是解释执行的 JS 模拟与绘制命令构建。V8 目前的原生解码平均为 2.62 ms，高于 QuickJS 的 1.42 ms，仍可继续优化。GPU 查询平均分别为 0.48 / 1.81 ms；图形驱动调度和设备频率会随提交速度变化，不能把这个差值解释为后端修改了 GPU 绘制算法。

当前验收通过 97 次宿主调用、每后端 232 个仿真案例 / 139,200 帧，以及每后端 840 帧实际应用录制/持久化读回/回放。两后端游戏统计快照和回放末状态严格一致。V8 与 Node 的额外原始实体字段也全部一致；QuickJS 在 24 案例中有 1128 个末位差，最大绝对差 `5.684341886080802e-14`，均单独记录。

24 个应用图形场景与 5 个通用 GPU 夹具的完整最终快照全部严格相等，没有实际使用浮点容差；29 对 PNG 文件字节与每个解码 RGBA 通道完全相同，变化像素为 0。四组性能场景的全部 16 次运行也通过状态/图像比较。

可复核的单一入口是 `reports/backends/report.json`，它汇总四份 scope 报告，要求它们的二进制与生产 JS 哈希均与当前文件一致。上述窗口的 V8 P95 在 16.67 ms 预算以内；这不是所有阶段、所有时间点、所有机器或实战输入都稳定 60 FPS 的保证。
